- 五条精确 GET：`GET /api/v1/episodes`（`limit` 默认 50、上限 200，`offset`、`run_id`、`recording_status`、`episode_id`）、`GET /api/v1/episodes/{episode_id}`、`GET …/streams`、`GET …/streams/{stream_id}/records`（`limit/offset/event_seq_from/event_seq_to/time_base/time_from/time_to`）、`GET …/assets/{asset_path}`（可选 64 位十六进制 `sha256`）。所有响应都声明 `schema_version=unirobot-mobilecar-episode-read-1` 与 `read_only=true`，客户端对不符合该 schema 的载荷直接拒绝，不做乐观渲染。
- 身份：列表行与详情都携带 `source_id + run_id + episode_id`，并保留 `adapter_id / native_contract_version / episode_directory / segments[].recording_segment_id / previous_recording_segment_id`；`backend_generation` 是 `{available,reason,distinct_values,scope}` 而非每条记录的字段，界面按该结构显示。`episode_display_name_is_not_a_key=true`，因此请求一律带 `run_id`；同名歧义由服务端 409 `episode_id_ambiguous`（`detail.runs`）表达，界面列出候选 run 并要求显式选择，不跨 run 串读。
- 完整性分五层显示：`declared.*`（记录自述）、`integrity.status`（`complete|incomplete_terminal_recorded|finalize_failed_missing_tail|unknown`）、`declared.complete_tail_file_present`、`integrity.checksum_verification`（声明条目数、本次重算文件、matched/mismatched 明细与 verdict）、`integrity.not_verified`。实测所选 COMPLETE 记录 `verdict=mismatch_present` 且不符只限 `episode.json`，与后端记录的“先写 tail 后定稿 episode.json”过期自校验一致；FAILED 记录 `status=incomplete_terminal_recorded` 而 tail 存在。界面只在被证据限定的情况下给出该解释，其余不符一律写“原因未证明”，并从不合并成“全部完整/已验证完整”。前端不调用 validate 或任何写入来“修复”显示状态。
- 时间与播放：可选时间基来自 `detail.time.available_time_bases[stream]`（实测只有 events/control 为 `backend_monotonic_s, sim_time_s, wall_utc` 与 observations-index 为 `arrival_time_s, measurement_time_s, sim_time_s`；observations-persist、transforms 不在该映射里），单位与 `clock_id` 逐条按记录原值显示；`cursor.line_index_is_not_a_clock=true`，行号不参与时间换算；`records_without_the_selected_base` 按服务端计数显示，缺时间字段就是“无该时间字段”，不补 0、不假设帧率。分页读取本身不带 `time_base`（服务端要求 `time_base` 必须伴随区间，否则 400 `time_range_required`），只有“定位”才带 `time_base + time_from`。**是否接受数值区间以服务端每页返回的 `time.numeric_time_bases` 为准**（实测 4 个 `*_s` 基），不再用“等于 wall_utc”这种名字判断；`wall_utc` + 数值边界返回 400 `time_base_not_numeric` 并附 `numeric_bases`，界面据此拒绝定位而不猜日历格式。`time.synchronized_across_streams=false` 时“跨流未同步”持续可见。
- event_seq 区间过滤（本轮实测）：`event_seq_from/event_seq_to` 是记录页的受支持参数，启用时后端把缺失、非整数或布尔 `event_seq` 的行**排除并计数**（`filtering.event_seq_range.excluded_without_valid_event_seq` + `anomalies[].{line_index,reason,value_type}`，reason 实测为 `event_seq_missing_or_not_integer`），并给出 `note`。实测同一 COMPLETE 记录：observations-index 3038 行、observations-persist/transforms 各 303 行全部被排除（原生 `SensorObservation` 不带 `event_seq`，persist 用 `persist_sequence`），HTTP 仍是 200 空页且 `next_offset=null`、`has_more=false`。界面把这种空页解释为“该流合法地没有 event_seq”，与“窗口内无匹配”“offset 越过末尾”三种情形分开表达；空页不再显示上一条记录的媒体，也不会退化成读取失败。
- 媒体：只按记录**自身携带的引用字段**读取。两种真实形状都在 18964 上验到：`observations-index` 用 `asset_uri` / `valid_mask_uri`，而 lidar/imu/encoders 这类记录的 `asset_uri` 合法地为 `null`（界面写“该记录没有引用”，不按 `sample_id` 猜文件名）；`observations-persist` **没有** `asset_uri`，改用 `rgb_uri` / `depth_uri` / `valid_mask_uri`（实测 `assets/rgb/rgbd_<id>_rgb.png`、`assets/depth/rgbd_<id>_depth_m.npy`、`assets/masks/rgbd_<id>_valid.png`，`kinds=[rgb,depth]`）。默认读取记录自带的 rgb 引用并显示解码结果，其余引用逐条列出并可单独读取；`.npy` 是 `application/octet-stream`，按字节读取并明确“不能内联显示”。声明摘要优先取记录字段（`asset_sha256` / `valid_mask_sha256` 等，实测这些记录为 `null`），否则取 `media_summary.kinds.<kind>.sample`（每类只带 20 条样本，实测每类 303 个文件、`declared_sha256_coverage=20/20`）；`media_summary.symlink_or_escape_excluded` 与 `excluded_count` 一并显示。声明摘要、本次服务端重算（`X-Episode-Asset-Sha256`）与完整性结论是三行各自的话。错误码原样显示：404 `episode_asset_missing`、409 `episode_asset_digest_mismatch`（`expected`/`actual`）、415 `episode_asset_type_unsupported`、400 `episode_asset_path_invalid`、413 `episode_asset_too_large`、409 `episode_asset_escape`。
- 记录页完整性字段形状：`integrity.lines_over_read_size_limit` 是**行号数组**（不是对象数组），`corrupt_lines[]` 另带 `column`；`identity.backend_generation` 在没有 events 的记录里是 `{available,reason,values,scope}`，有记录时是 `distinct_values`，界面取任一非空列表显示，不宣称每行都有 generation。不可用流带 `reason=stream_not_recorded_or_missing`，被扫描上限截断的流带 `scan_truncated=true`，JSON 流解析失败带 `parse_error`：三者都按原文显示，`available=true 且 records=0` 的流仍可打开（空页是结果，不是不可用）。
- 上游差异与错误面：统一候选 18959 不提供 episode 读取路径，历史视图在该上游如实显示网关拒绝。episode-read-1 的首个切片是 `m1k-20261025T040435Z-platform`（常驻 18960，前端上一轮在此验收）；本轮按后端整改后的候选 **`m1p-20261025T053030Z-platform`（`http://127.0.0.1:18964`，服务器 PID 2102683）** 重新核对并完成真实历史验收，两代候选都继续存活、不互换、不推断。新增错误码已进入界面：404 `episode_stream_unavailable`、400 `episode_id_invalid`、400 `run_id_invalid`、409 `episode_path_escape`、502 `episode_record_corrupt`、500 `history_source_invalid`、503 `history_source_unavailable` / `history_source_not_configured`；FastAPI 参数校验（`limit>200`、`offset<0`、`sha256` 非 64 位小写十六进制）经代理返回 422，其 `detail` 是数组，客户端归为 `validation_error` 并原样显示消息（旧的前端把 `http_422` 当码名，实际永远不会命中）。路径越界类（`history_path_escape` / `episode_asset_escape`）只能在直接对上游时出现，网关按结构拒绝点分段。后端的只读整改与可复现发布不等于历史归档全量验证，因此本切片仍不算正式 M1.5 验收。

- **仍未解除的阻塞**：当前运行的 18949 与 18953 的 OpenAPI 都不含 `/sessions/{id}/stop` 与 `/recording/end`，8792 未部署 native `m1h` 补丁，生产 recipe `mobilecar.g1.teleop` 只声明 `session_binding`+`recording_begin`；因此真实环境里 STOP/结束录制恒为 unsupported，前端按钮禁用并显示该原因。带成功回执的分层显示只在明确标注 `?fixture=synthetic-lifecycle` 的合成夹具中验证，不是真实 native、真实停车或 M1 验收证据。
- 异步归属规则（本轮补强）：路线写入（创建/条件保存/409 重试/发布/重载）绑定“发起时的上下文”（`epoch` + 当时的 `route_id` + 当时的 `mapId/mapVersion` + 挂载状态）。地图被成功采纳、切离线、打开另一条路线、`closeRoute` 解除绑定、组件卸载都会推进该上下文；迟到的响应一律不套用，包括不清除新请求的 `busy`、不写回 `?route=`，并显式提示“服务端可能已受理该写入，请重新读取”。AbortController 不被当作撤销服务端已受理写入的保证，因此这些请求故意不 abort。Session 侧同理：`recoverOne`/`refreshCurrent` 归属发起时的 `selectionEpoch` 与当前 `session_id`，只按 id 更新存档缓存（`mergeSession`），不改变当前选择，也不在新选择读取中插入覆盖性的 current 刷新；恢复读回使用独立信号，取消一次意图不连带取消对账读回。
- 地图侧修复：一次地图选择 = 一个事务（`mapSerial` + 共享 `AbortController`），版本详情、PGM 字节、SHA-256 摘要与栅格尺寸校验串在同一条链上并全部在 `live()` 判定之后才写状态；切离线、开另一条路线、卸载都递增序号并 abort 在途控制器，晚到的成功/失败不覆盖新选择。写入资格统一为 `gates.{create,save,publish,retry}`，要求“当前路线绑定的真实地图”通过摘要+尺寸校验（`imageEvidence.mapId/mapVersion` 必须等于该地图，不只是非空）、不处于 loading/failed/offline、位置与朝向有效；关闭时动作显式拒绝并写“写入未发出”。发布结果绑定服务端修订：`data-publish-revision`/`data-publish-version`/`data-publish-digest`，存在未保存本地编辑时 `data-publish-dirty=true` 并明确提示本地编辑未被发布。
