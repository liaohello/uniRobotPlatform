# 文档组织与维护规则

规范 ID：`GOV-MAINTENANCE` · 状态：本轮文档组织建议。

## 四级阅读结构

总索引 → 大类 → 功能包 → 规范节点。大类与功能包各有 README；编号节点内写具体规则，不再按每个按钮建立空文件。

前端主目录按工作区及共享交互组织，界面区域另作索引；后端按能力域与子功能组织。协议由 Contracts 主责，工作区引用共享工具，验收引用规则，历史总册作为来源保留。

## 三种状态分别记录

| 维度 | 示例 | 不能推断 |
|---|---|---|
| 需求确认程度 | 用户明确、历史基线、建议、未决、当前排除 | 进入目录不等于用户确认 |
| 文档成熟度 | 基础草案、详细设计、冻结、被取代 | 写了规范不等于已开发 |
| 实现/验证状态 | 未实现、已实现未验证、已验证并有证据 | 链接有效不等于产品测试通过 |

## 单一主责

- 前端：用户看到什么、怎样操作、怎样反馈。
- 后端：状态与控制由谁裁决、计算/执行/持久化怎样发生。
- 共享契约：身份、时间、单位、命令、数据与跨边界语义。
- 功能包索引：入口、边界、依赖，不复制节点正文。
- 系统总览：目标和跨域关系，不变成实现细节的杂物箱。

后端节点当前是责任拆解草案，不把未核对的函数名、端点、传输或频率写成事实。已有工程调查是参考，不自动覆盖更新的用户需求。

## 变更流程

1. 先判断新材料是用户决定、建议还是运行证据；来源进入来源登记。
2. 使用现有主责节点；仅在功能可独立设计/验收时再拆节点。
3. 更新稳定 REQ、相关 DEC/OQ 与取代关系，保留旧来源。
4. 修改跨边界语义时同步 Contracts 和前后端消费节点。
5. 在未决收敛后补验收预期，再记录实际实现/测试证据。
6. 更新功能索引、需求矩阵与机器可读目录；不要为索引复制整段规则。

文件夹编号用于浏览排序，文档 ID 用于引用；移动文件时保留 ID，并更新入链。节点从 01/02/03 逐步增加即可，不用日期给每次小改动新建一整套 Spec。

## 机器可读文件

`catalog.json` 记录当前节点和功能包；`traceability.json` 记录原始及新增需求、主责规范、来源和 TEST。它们与 Markdown 索引同步维护，不是 API schema，也不代表功能状态。
